<a id="uptane"></a>
## Uptane：规定信任关系，不替你写 Flash

Uptane 用 Image 与 Director 等仓库角色、元数据及 ECU 角色组织车辆更新的信任关系。它回答更新来源、目标分配与验证的问题；镜像怎样下载、写入、切换分区和恢复，仍由具体系统实现。[规范源文件](https://github.com/uptane/uptane-standard/blob/master/uptane-standard.md)

采用时先画出本项目的仓库、签名、Primary/Secondary ECU 和时间来源，逐项映射到所选实现。验证用例应覆盖元数据过期、映像与目标不匹配等情况，并记录拒绝发生在哪个阶段。一个安装器能验证包签名，不代表它已实现完整 Uptane 角色和元数据流程。

<a id="rauc"></a>
## RAUC：安装成功之后还有启动健康确认

RAUC 围绕签名 bundle、slot 配置和引导程序集成组织更新。写入非活动 slot 后，新系统是否健康仍由产品逻辑判断，再执行相应的 good/bad 标记；回退也依赖引导程序与配置的配合。评估重点是这条闭环，而不只是更新命令退出码。[更新与启动确认](https://rauc.readthedocs.io/en/latest/using.html) · [基本机制](https://rauc.readthedocs.io/en/latest/basic.html)

在可恢复的 A/B 台架上，准备正常镜像与“能启动但关键服务不健康”的镜像，检查何时确认、何时耗尽重试以及回到哪个版本。确认条件应包含产品真正依赖的服务，不能在进程刚启动时就无条件标记成功。

<a id="swupdate"></a>
## SWUpdate：安装灵活性来自描述文件与 handler

SWUpdate 用 `sw-description` 描述 SWU 包中的安装对象，并通过 handler 处理不同镜像、分区或安装步骤。它适合更新流程具有多种对象和产品定制逻辑的场景。签名验证、硬件兼容检查和回退行为要落实到具体构建与配置，不能只看一个成功安装示例。[包格式、描述文件与 handler](https://sbabic.github.io/swupdate/swupdate.html)

把产品更新拆成明确步骤：校验、写入、状态持久化、启动切换和确认。对每个可中断点记录重启后的预期状态，再检查自定义 handler 是否满足这一约定。比较 RAUC 与 SWUpdate 时，重点是自己的分区布局和定制安装成本，而不是谁的功能清单更长。

<a id="mcuboot"></a>
## MCUboot：试启动回退取决于镜像模式和确认

MCUboot 将通用启动逻辑与平台相关引导分开，支持不同镜像更新方式。采用支持试启动的交换流程时，应用确认镜像后才将其保留；未确认可在后续启动时回退。覆盖式更新、直接执行等模式有不同条件，不能统一描述成“自动 A/B 回滚”。[镜像布局、交换与确认机制](https://docs.mcuboot.com/design.html)

先用目标芯片的 Flash 擦除粒度、镜像头尾和槽位布局计算空间，再在可恢复开发板上验证正常更新、错误签名与试启动未确认。业务故障回退和阻止安装旧漏洞版本的安全策略是两件事，版本选择应同时满足它们。

## 一份更新方案至少交接哪些材料

交付应包含角色与密钥职责、包或元数据格式、目标分区布局、安装配置、健康确认条件及恢复步骤。测试记录区分下载失败、校验拒绝、写入中断、首次启动失败和应用不健康，才能看出失败被哪一层处理。

这些材料用于检查整个更新流程，不能由任何单一项目的功能标签替代。
